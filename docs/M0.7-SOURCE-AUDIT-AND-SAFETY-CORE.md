# M0.7 — Source audit and settlement safety core

## Source-derived findings

The reviewed repository already has a working Sandbox authorize flow, PostgreSQL transaction and policy-run persistence, live Channel3 search/refresh, a deterministic evaluator, and a local single-user evidence-review workflow. The policy lab and live discovery routes are explicitly side-effect free with respect to PayPal.

The key safety gap was that the live discovery evaluator reconstructed its offer only from the Channel3 snapshot and did not consume the Evidence Desk's human-reviewed records. The data was stored, but it did not influence that live decision. The second gap was that audit events were ordered and persisted but not hash-chained. The third gap was that the policy run did not persist the exact pact specification, making a future transaction-bound settlement decision harder to verify.

## What this patch changes

- The live-offer evaluator now reads evidence records for the exact snapshot and passes only content-hash-valid `HUMAN_REVIEWED` + `source_inspected` claims into evaluation. Their source, observation time, validity deadline, and snapshot subject reference are retained. The evaluator considers all valid reviewed claims, so multiple fresh conflicting claims block rather than silently accepting the newest value.
- Persisted evidence hashes are recomputed before policy evaluation. A mismatched hash is counted as an integrity failure and lowers the security gate, which blocks the evaluation. The hash detects content drift only when the stored hash itself is unchanged; it is not a keyed signature or protection against a privileged writer who can alter both content and hash.
- Policy runs now store the exact pact JSON and a SHA-256 integrity hash over the pact, offer snapshot, and verification result. This is an integrity reference, not a digital signature or an access-control boundary.
- Audit events are hash-chained per transaction. Legacy events are backfilled only when every existing row has both hash fields absent; a partially populated chain is rejected instead of silently recomputed. Transaction reads report whether the chain verifies. A hash chain is tamper-evident if the expected head is independently retained; a database administrator who can rewrite the entire database can recompute a chain.
- PayPal authorization recording now rejects results unless the local transaction is in `AUTHORIZING`, and duplicate responses are idempotent only when the persisted authorization ID, statuses, amount, and currency match exactly.
- A pure settlement state-transition model and gate predicate define the future guarded-capture preconditions—including an explicit requirement to revalidate that the authorization has not expired—and are unit-tested. They are not yet connected to a PayPal capture route.
- Transaction schema/state types are prepared for verification, capture-review, voiding, and external outcome reconciliation states, and transaction reads include audit-chain verification.

## Explicitly not included yet

There is deliberately **no PayPal capture endpoint in this patch**. The current authorizing transaction flow still does not bind an approved pact, live offer snapshot, current evidence set, and authorized amount into one transaction record. Exposing capture before that binding is implemented would be unsafe. M0.8 must add that relationship and re-evaluate current evidence server-side at settlement time before any capture/void call.

The Evidence Desk remains a local single-user human-attestation prototype. It does not fetch or authenticate retailer pages and must not be exposed publicly until authentication, authorization, source-fetch/SSRF protections, rate limiting, and deployment hardening are added.
