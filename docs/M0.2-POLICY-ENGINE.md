# M0.2 — Deterministic Purchase Pact Evaluation

## Purpose

M0.2 introduces a deterministic evaluator for a structured `PurchasePact` and one exact `OfferSnapshot`. It performs no network calls and cannot capture, void, or otherwise move money. It creates a `VerificationResult`; `decideSettlement` returns a policy recommendation only.

## Safety conditions

A positive decision is possible only when all of the following are true:

1. The caller explicitly reports `securityClear: true`.
2. Evidence required by every hard constraint is fresh at evaluation time.
3. That evidence has a source reference and is bound to the exact offer ID.
4. Each hard constraint evaluates to `pass`.
5. At least one hard constraint is present; a soft preference cannot be the only policy.
6. The offer currency matches the currency encoded in the pact.

Missing fields, invalid comparisons, expired/missing evidence, mismatched evidence, duplicate constraint IDs, invalid budgets, and absent hard constraints fail closed. Unknown is not treated as pass.

Soft preferences are evaluated and surfaced but do not block a purchase when hard constraints pass. Legacy `ConstraintResult` records that omit `severity` are treated as hard to preserve fail-closed behavior.

## Evidence contract

Every evidence record used for a hard constraint must include:

- `field`: exact field/path it supports, e.g. `total` or `attributes.ramGb`;
- `subjectRef`: the exact `OfferSnapshot.id`;
- `provenanceRef`: a non-empty source pointer;
- `collectedAt` and `validUntil` timestamps;
- `value` consistent with the current offer snapshot.

Conflicting fresh evidence results in `unknown`, not a model-selected winner. Evidence freshness is evaluated against an injectable clock to make tests reproducible.

## Currency and amount rules

Currency equality is enforced by a synthetic hard constraint. If `maxTotalAmount` is set, the evaluator always adds a separate hard total cap—even when an explicit budget constraint also exists—so conflicting limits are resolved by their stricter intersection, never by silently ignoring one. Currency/amount are never converted implicitly; the snapshot currency must match the pact currency.

## Tests

`packages/pact-core/test/policy.test.ts` covers compliant offers, attribute downgrade, budget overrun, expired evidence, wrong offer binding, conflicting evidence, currency mismatch, failed security check, missing hard constraints, and empty verification results.

## Boundary

An output decision of `capture` means only “the current structured policy preconditions passed.” It is not a PayPal operation and must never be wired directly from an LLM output. A later settlement service must re-fetch/revalidate the authorized PayPal state and implement an explicit, separately tested state transition before any capture can exist.
