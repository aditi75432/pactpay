# M0.5 — Live catalog refresh and drift observation

## Objective

Turn the original Channel3 search result into an immutable, versioned catalog observation by refreshing it through Channel3's documented Product Detail endpoint and comparing the returned current offer against the previously selected product+merchant pair.

## Safety semantics

A successful refresh is **not** a settlement decision. It may update only facts present in Channel3's product-detail response. It does not prove the checkout total, tax, shipping, delivery commitment, return window, or fulfillment completion.

## Identity rule

1. Product ID must equal the server-stored product ID.
2. Merchant domain must match the prior snapshot.
3. Prefer a match on canonical HTTPS offer URL host+path; ignore tracking query parameters only.
4. If the path does not match, permit a merchant-domain fallback only when exactly one offer exists for that product+merchant.
5. Ambiguous or absent matches produce `OFFER_NOT_FOUND`. They must not silently switch to another merchant.

## Snapshot and comparison

On a match, write a **new** `pactpay_channel3_offer_snapshots` row and a `pactpay_channel3_refresh_checks` row in one database transaction. Never rewrite the old snapshot. The comparison covers title, item price, currency, availability, condition, and structured RAM. Values missing from the new response remain unknown; they are not imputed from a product title.

## API

`POST /api/discovery/refresh`

Request:

```json
{ "snapshotId": "<server-stored snapshot UUID>" }
```

Successful match returns `MATCHED_UNCHANGED` or `MATCHED_WITH_CHANGES`, a new `refreshedOffer` snapshot, changed fields, and `paymentAction: "NONE"`. A non-unique/no longer available merchant offer returns `OFFER_NOT_FOUND`, preserves the old snapshot, and instructs the caller to run a fresh search.

## Threat boundaries

- The route only calls a fixed Channel3 API hostname; it does not fetch arbitrary merchant URLs.
- Product IDs are read from the server database and validated before path construction.
- Channel3 API credentials remain server-side.
- Network redirects are rejected, requests have a 12-second timeout, and upstream error messages are sanitized.
- No PayPal mutation is performed.

## Acceptance checks

- Core TypeScript typecheck and test suite pass.
- Web TypeScript typecheck passes.
- A live refresh returns a matched offer or a clear fail-closed non-match.
- On match, the new snapshot ID differs from the original ID.
- The price/availability/condition/RAM comparison is visible.
- Database retains both prior and refreshed snapshots plus their refresh-check record.
- No PayPal order/authorization/capture/void is triggered.
