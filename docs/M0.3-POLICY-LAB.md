# M0.3 — Policy Lab integration

## Purpose

Expose the deterministic PactPay policy evaluator through a working UI and server-side API, with a persisted history of fixture evaluations.

## Routes

- `GET /api/pacts/runs` — return the last 20 persisted policy runs.
- `POST /api/pacts/evaluate` — accepts only a server-defined `{ "scenarioId": "..." }`; generates a deterministic simulated offer and evidence, runs `evaluatePact`, persists the result, and returns the verification trace.
- `/pact-lab` — scenario selector, constraint-result trace, evidence/security gate status, and persisted history.

## Scenarios

`compliant`, `budget_overrun`, `ram_downgrade`, `delivery_slip`, `return_policy_downgrade`, `stale_evidence`, `conflicting_evidence`, `currency_mismatch`, and `merchant_instruction`.

Every scenario is explicitly simulated. The `merchant_instruction` fixture sets the security result to false to test the fail-closed branch; it does **not** claim to provide an autonomous prompt-injection detector.

## Safety properties

- Scenario IDs are allowlisted server-side; the browser cannot submit arbitrary policy or offer objects.
- The API uses deterministic fixtures and the same policy package tested in M0.2.
- Each evaluation is persisted in `pactpay_policy_runs`.
- A policy pass is only an evaluation result. `paymentAction` is always `NONE`; no authorize/capture/void operation is made by this API.
- This lab does not represent Channel3 product data or live merchant evidence.

## Apply and validate

Merge this patch over the PactPay repository, keep `.env.local` untouched, then run:

```powershell
pnpm install
pnpm --filter @pactpay/pact-core typecheck
pnpm --filter @pactpay/pact-core test
pnpm --filter web typecheck
pnpm dev
```

Open `http://localhost:3000/pact-lab`, run the compliant scenario and at least three blocking scenarios, then restart the application and refresh history to verify persistence. PostgreSQL must be running (`pnpm db:up`).
