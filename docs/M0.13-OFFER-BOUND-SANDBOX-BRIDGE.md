# M0.13 — Channel3-bound PayPal Sandbox test checkout

## Purpose

Connect the existing live Channel3 discovery flow to the existing protected PayPal Sandbox settlement gate without claiming that Channel3 currently places a real order at the displayed merchant.

## End-to-end flow

1. The shopper searches Channel3 and reviews an approved Purchase Pact in the Pact Composer.
2. Discovery displays persisted Channel3 offer snapshots. The user selects an offer and clicks **Test selected offer in PayPal Sandbox**.
3. The browser posts the saved snapshot ID and Pact to `POST /api/paypal/offer-demo/orders`, together with explicit acknowledgement of the Sandbox test quote.
4. The server reloads the snapshot from PostgreSQL, checks that it is current and in USD, requires an explicit positive availability state, sanitizes the Pact, and evaluates all hard constraints before creating any PayPal order.
5. The server builds a Sandbox-only test quote from the current Channel3 item price, plus a **simulated** $4.99 shipping term and **simulated** 8% test tax. It stores the immutable source snapshot ID on the transaction and binds the approved Pact and offer evidence into the protected context.
6. PayPal Sandbox creates an order with intent `AUTHORIZE`. The buyer approves the virtual Sandbox transaction and returns to the protected page.
7. The user can run a baseline or controlled drift scenario. Scenario mutations are stored in PactPay's server-side test context and do not rewrite the immutable Channel3 snapshot or make a PayPal API request by themselves.
8. Before the settlement gate runs, the server queries Channel3's Product Detail endpoint again, verifies the same product ID and unique product-plus-merchant offer, persists the new observation and refresh comparison, and rebuilds test evidence from that observation.
9. The server re-queries the PayPal authorization, verifies transaction/Pact/source snapshot/audit bindings, and evaluates the deterministic gate. A verified pass may capture the bound Sandbox authorization. A block attempts to void the authorization. Uncertain states fail closed and require reconciliation.

## Controlled test scenarios for the bound-offer path

- `BASELINE`: use the latest matching Channel3 catalog facts with the saved test quote.
- `PRICE_INCREASE`: modify the test item's price after buyer approval; the live Channel3 snapshot is not modified.
- `OUT_OF_STOCK`: mark availability out of stock in the test fixture only.
- `CURRENCY_MISMATCH`: deliberately change the test quote currency to exercise amount/currency binding.
- `PROMPT_INJECTION`: set a controlled, explicitly labelled untrusted-instruction finding. This is a fixture for fail-closed behavior, not a claim that live merchant content has been detected or classified.

The legacy fixed-laptop simulator remains available only as a repeatable fallback lab; it is no longer the primary entry path shown when opening the protected Sandbox lab.

## Evidence and checkout boundaries

**Live from Channel3:** selected product/merchant listing, item price, currency, reported availability, condition and structured attributes where supplied, plus fetched time, validity window and source URL.

**PactPay test fixture:** shipping ($4.99), test tax (8%), resulting Sandbox authorization amount, and deliberate mutation scenarios. These are not merchant checkout terms, not taxes calculated by a tax provider, and not a final retailer price.

**PayPal Sandbox:** actual developer API calls and sandbox transaction state using virtual funds. This does not transfer real money or place an order with the retailer shown in Channel3.

## Fail-closed invariants

- Snapshot ID on the transaction must match the approved context's original snapshot ID.
- The same Channel3 product plus merchant offer must be uniquely matched immediately before settlement.
- Unknown or negative availability is not eligible for payment.
- Currency changes away from USD and unsupported/non-positive refreshed price ranges are recorded as failed revalidation, so the gate can block and attempt to void rather than treating the changed listing as a successful checkout.
- Missing or stale required evidence does not pass a hard constraint.
- The current test quote must still match the amount/currency authorized in PayPal Sandbox.
- Policy and audit checks run server-side. Groq cannot receive capture authority.
- Reconciliation is read-only toward PayPal and does not issue a second capture.

## Run and verify

From repository root, run:

```powershell
pnpm --filter @pactpay/pact-core typecheck
pnpm --filter @pactpay/pact-core test
pnpm --filter web typecheck
pnpm test
pnpm dev
```

Then search in Channel3, approve a Pact, choose an offer with a fresh USD snapshot and explicit positive availability, acknowledge the Sandbox test quote, approve the PayPal Sandbox authorization, and run the baseline gate. For a negative test, start a new offer-bound Sandbox checkout and choose a test mutation before settling. Never retry a transaction after it reaches a terminal state or an uncertain settlement/reconciliation state.
